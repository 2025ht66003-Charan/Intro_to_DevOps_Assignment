1   CI/CD Architecture Overview

The pipeline follows a Source → Build → Test → Quality → Package → Deploy lifecycle, implemented in parallel across two CI/CD engines: Jenkins (primary, on-premise) and GitHub Actions (cloud-native, triggered on every push). Both converge on the same Docker Hub registry and Kubernetes cluster.

Deployment Strategies

Five zero-downtime strategies are implemented as independent Kubernetes manifest sets under k8s/, each with its own rollback mechanism:

StrategyMechanismRollback
Rolling Update maxUnavailable: 1, maxSurge: 1 — incremental pod replacement kubectl rollout undo
Blue-Green Two identical deployments; Service selector switches slot label Patch selector back to slot: blue via rollback.sh
Canary 9 stable + 1 canary replica → ≈10 % traffic to new version kubectl delete deployment aceest-canary
Shadow Primary serves users; shadow receives mirrored traffic silently Delete shadow deployment; zero user impact
A/B Testing Nginx Ingress canary-weight: 50 splits traffic between two Services Remove canary Ingress; all traffic returns to Version A

2   Challenges Faced & Mitigation Strategies

ChallengeRoot CauseMitigation
Alpine package installation failure
apk add gcc returned TLS error inside Docker build 		Self-signed certificate in the build environment's proxy intercepted HTTPS to Alpine CDN; dl-cdn.alpinelinux.org returned certificate not trusted. Switched base image from python:3.11-alpine to python:3.11-slim (Debian). Flask and Gunicorn ship as pure-Python wheels, so gcc is not needed.
PyPI unreachable inside Docker
SSL certificate verify failed for pypi.org 		The container network egress was blocked at the SSL layer; pip install exhausted all retries. Pre-downloaded all wheels on the host with pip download -d wheels/ (which uses the host's trusted proxy cert), then built the image with --no-index --find-links=./wheels — completely offline inside Docker.
Debian apt-get also blocked
403 Forbidden from deb.debian.org 		Same outbound proxy restriction; apt-get update could not reach the Debian mirrors. Eliminated apt-get entirely from the Dockerfile by choosing a single-stage build with only pure-Python packages — no system compilation dependencies required.
No live Kubernetes cluster
Minikube not installed; kubectl not present 		The assignment environment only had Docker available; Minikube requires nested virtualisation or a bare-metal node. Simulated all five deployment strategies as named Docker containers on distinct host ports (5000–5006), each with the correct environment label. Kubernetes YAML manifests are production-ready for real cluster deployment.
SonarQube server not available
No running SonarQube instance; sonar-scanner not in PATH 		SonarQube requires a persistent server process; spinning up the Docker image requires outbound connectivity for setup. Generated a self-contained SonarQube-style HTML report (sonarqube_report.html) from real data: pylint, radon, coverage.py, and pytest — covering all metrics SonarQube would produce. sonar-project.properties is ready for a live server.
Managing five deployment manifests consistently Each strategy required its own Deployment, Service, and sometimes Ingress — risk of drift between manifests. Structured k8s/ as a flat directory per strategy, each with a dedicated rollback.sh. A universal k8s/rollback/rollback.sh accepts a strategy argument, unifying rollback across all deployments.
